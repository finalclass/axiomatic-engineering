# Plan: Migrate axioms-sync to OpenRouter API

## Overview
Replace CLI-based AI access (Claude/Kilo) with direct OpenRouter API calls, maintaining backward compatibility with existing CLI mode as optional fallback.

## Key Design Decisions

### Config Location
- New path: `~/.config/axioms-sync/axioms-sync.toml`
- Fallback to `~/.config/archea/archea.toml` for backward compatibility during transition
- Config structure:
```toml
[openrouter]
api_key = "sk-or-v1-..."

[general]
# Optional: "openrouter" | "cli" - default: "openrouter"
provider = "openrouter"

# model mappings (optional overrides)
[models]
opus4.6 = "anthropic/claude-opus-4-6"
sonnet4.6 = "anthropic/claude-sonnet-4-6"
```

### Module Structure
```
lib/ai_access/
  ai_access.ml          # Factory/wrapper - selects provider
  ai_cli_access.ml      # Renamed from current ai_access.ml
  ai_openrouter_access.ml # New OpenRouter implementation
```

### API Compatibility
Both modules must implement identical signature:
```ocaml
type executor = Cli of string | Api of string

val dispatch :
  ~executor:executor ->
  ~model:string ->
  ~provider:string ->
  ~system:string ->
  ~prompt:string ->
  ~cwd:string ->
  ?quiet:bool ->
  unit ->
  (string * Types.cost_info option * string option, string) result

val dispatch_resume :
  ~executor:executor ->
  ~model:string ->
  ~provider:string ->
  ~session_id:string ->
  ~prompt:string ->
  ~cwd:string ->
  ?quiet:bool ->
  unit ->
  (string * Types.cost_info option * string option, string) result
```

## Implementation Steps

### Step 1: Rename and Isolate CLI Module
**File**: `lib/ai_access/ai_cli_access.ml`

1. Copy current `ai_access.ml` to `ai_cli_access.ml`
2. Change module name from `Ai_access` to `Ai_cli_access`
3. Keep all CLI-specific code (kilo/claude streaming parsers)
4. Remove model resolution that routes to CLI vs API
5. Keep `resolve_alias` and `estimate_cost_usd` for shared use

**Estimated**: 30 min

### Step 2: Create OpenRouter Module
**File**: `lib/ai_access/ai_openrouter_access.ml`

Implement direct API calls to OpenRouter:

1. **HTTP Client Setup**
   - Use `Cohttp_eio` (already available via well/eio deps)
   - Implement streaming response handler
   - Handle NDJSON format (OpenRouter streams events)

2. **Tool Loop Implementation**
   - Implement tool calling loop internally (unlike CLI which manages it)
   - Tools to support: `bash`, `read`, `write`, `edit`, `glob`, `grep`
   - Each tool returns result to model, continues conversation
   - Track conversation via `conversation_id`

3. **Request/Response Format**
   ```json
   {
     "model": "anthropic/claude-opus-4-6",
     "messages": [...],
     "tools": [...],
     "tool_choice": "auto",
     "stream": true
   }
   ```

4. **Session Management**
   - Map `session_id` to OpenRouter's `conversation_id`
   - Store conversation_ids in memory for resume

5. **Cost Tracking**
   - Parse `usage` from OpenRouter response
   - Use same pricing as `estimate_cost_usd`

**Estimated**: 4-6 hours (complex: requires implementing tool loop)

### Step 3: Create Factory Wrapper
**File**: `lib/ai_access/ai_access.ml`

1. Read config from `~/.config/axioms-sync/axioms-sync.toml`
2. Add `toml` library dependency to dune-project
3. Implement provider selection:
```ocaml
type provider = Cli | OpenRouter

let get_provider () : provider =
  match read_config () with
  | Some cfg when cfg.provider = "cli" -> Cli
  | _ -> OpenRouter  (* default *)
```

4. Delegate dispatch calls to appropriate module:
```ocaml
let dispatch ~executor ~model ~provider ~system ~prompt ~cwd ?(quiet=false) () =
  match get_provider () with
  | Cli -> Ai_cli_access.dispatch ~executor ~model ~provider ~system ~prompt ~cwd ~quiet ()
  | OpenRouter -> Ai_openrouter_access.dispatch ~model ~system ~prompt ~cwd ~quiet ()
```

**Estimated**: 1-2 hours

## Questions to Resolve

1. **Well.fetch availability** - Is `Well.fetch` already implemented? Need to verify or implement alternative.

2. **Streaming vs non-streaming** - OpenRouter supports streaming. Should we implement streaming for real-time output?

3. **EU Router** - Which specific EU router should be supported alongside OpenRouter? Need details.

4. **Ollama support** - Should we plan module structure for local Ollama support now, or defer?

5. **Tool result format** - OpenRouter uses OpenAI-style tool calls. Need to verify format compatibility.

## Risk Areas

1. **Tool calling loop complexity** - Most complex part. Requires careful state management.
2. **Token counting** - OpenRouter returns usage but may need estimation for streaming.
3. **Error handling** - Network failures, rate limits, need retry logic.
